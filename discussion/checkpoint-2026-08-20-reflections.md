# Reflections on the 20/08 tutor checkpoint — what it confirms, and what it opens

Source: [`../docs/checkpoints/checkpoint-2026-08-20-tutor-kickoff.md`](../docs/checkpoints/checkpoint-2026-08-20-tutor-kickoff.md) (factual summary, kept in Portuguese at Rafael's request) and [`../docs/sources/Checkpoint_Tutor_2026-08-20.docx`](../docs/sources/Checkpoint_Tutor_2026-08-20.docx) (transcript). This is the meeting the [20/08 diary entry](../research-diary/Ago/diario_campo_2026-08.md#20082026) flagged as "fluxos jurídicos mapeados, transcrição pendente de anexar" — it's attached now, closing that pending item.

## 1. The tutor independently confirms the harness-not-retraining decision — with the exact vocabulary

This is the most important thing in the transcript. Describing what he wants from the mechanism, the tutor says (unprompted, no leading question from Rafael): *"a gente vai anotando alguns casos ao longo do tempo... avalie aqueles que estavam certos, aqueles que estavam errados e se corrija, corrija a memória... A forma de fazer para tentar diminuir ao longo do tempo esses casos errados."* Rafael immediately checks the RL framing against that: *"Isso, mas aí é só reforçando, não retreinando"* — tutor: *"não retreinando."* Rafael then names the mechanism almost exactly as later formalized: *"Só mexendo no ar, no harness, talvez, criando uma skill nova, uma memória de procedure, alguma coisa assim que ele possa fazer um retrieval disso"* — tutor: *"Perfeito, exatamente isso."*

**Why this matters:** [`scope-and-terminology-decisions.md#2`](scope-and-terminology-decisions.md#2-what-reinforcement-learning-means-in-this-projects-title) already records the 20/08 decision ("harness adjustment... not SFT") as resolved via the formal-tutor channel, but without a citable primary source. This meeting *is* that source — the decision wasn't made in the abstract, it traces to this exact exchange. **Action taken:** the decision-log entry now links back to this transcript as its evidentiary basis (see the update to that file alongside this note).

## 2. The cross-agent confidentiality concern from 18/08 gets a real-world confirmation

[`scope-and-terminology-decisions.md#3`](scope-and-terminology-decisions.md#3-cross-trial-vs-cross-agent) narrowed the project's confidentiality concern to handoffs between distinct specialized agents, based on a definitional exercise. This meeting supplies the missing empirical half: at Itaú, pipeline-stage agents today **do not** talk to each other directly, and the tutor names the same two reasons the project's own scope narrowing anticipated — narrow, well-defined per-stage scope, and **security/compliance barriers to agent-to-agent communication specifically** ("não é tão simples um agente conversar com outro agente, isso tem barreiras de segurança também de compliance"). This is worth citing directly if Sub 2.2's architecture document needs to justify *why* cross-agent memory sharing is being treated as out of scope rather than just deferred — it isn't a theoretical concern, it's already a constraint the platform lives under.

## 3. The tutor's own trigger design is already the mitigation `thumbs-feedback-reliability.md` recommended

[`thumbs-feedback-reliability.md`](thumbs-feedback-reliability.md) (this same day, before this transcript was reviewed) recommended, from RLHF literature, that a single noisy thumbs-up/down should be treated as a candidate for review rather than an automatic trigger — aggregating signal before committing a memory write. The tutor's own mental model of the trigger, described independently, is a **volume- or time-based batch review**: "juntei mais 100 avaliações aqui desse case... vamos avaliar e ver se precisa atualizar a skill, a memória." That's the same shape of answer, arrived at from a completely different direction (operational necessity, not RLHF noise concerns). This is a convergence worth keeping: it means the noise-mitigation design isn't a research add-on being proposed against the grain of the project's needs — it's already how the tutor was picturing the update cadence. Strengthens the case for treating "batch of N annotated cases" (not "single interaction") as the natural unit of update for Sub 2.2/Sub 3.1, and gives Sub 1.5's acerto/erro criteria a concrete scale to design around (~100 cases, not 1).

## 4. New scope question: business rules already have a home that isn't agent memory

The "grande causa" threshold example (business-unit-owned, changes anytime, exposed as an MCP tool returning `true`/`false` rather than baked into any agent's context) shows Itaú already has an established pattern for **fast-changing structured facts**: a live tool call, not a memory write. That's a boundary the project's memory-update mechanism should probably respect rather than duplicate — updating an agent's memory to reflect "the threshold is now 500k" would be redundant with, and could drift out of sync with, the MCP tool that already owns that fact live. **New open item** (added to `open-questions.md`): should the mechanism's design explicitly scope out "facts servable by an existing business-rule MCP tool" from what memory updates are allowed to touch, to avoid two systems of record for the same volatile fact?

## 5. New scope question: signal capture likely needs two designs, not one

Sub 3.1 ("captura e armazenamento dos sinais de desempenho") has so far been discussed as if there's one signal-capture point. This meeting shows agents run in **two structurally different modes** — copilot/chat (a human is already present, could plausibly tap thumbs up/down directly) versus systemic/event-driven via Kafka (no human turn exists at all in the interaction itself). A thumbs-up/down UI affordance has an obvious home in the first mode and none in the second — the second mode's "correctness" signal has to come from somewhere else (a downstream review process, ex-post annotation against outcomes like won/lost cases or reversed decisions). **New open item** (added to `open-questions.md`): does Sub 3.1 need two distinct signal-capture designs, one per interaction mode, or does the systemic mode simply get its cases into the same "batch of N annotated cases" pool through a different collection path?

## 6. Grounds the project's abstract urgency in a concrete number

The work plan's Objetivos motivate the mechanism abstractly ("evitar depender de tantas pessoas validando"). This meeting supplies the actual scaling curve behind that sentence: ~2 agents in production by end of 2026, ~6 by mid-2027, 20+ the year after — against a ~1,000-person legal operation today. Worth keeping as the concrete number to cite in the M1 report's motivation section instead of the more abstract framing alone.
