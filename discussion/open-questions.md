  - **How does the Write Transform read the agent's short-term memory in a framework-agnostic way?** Each framework stores trajectory differently: Hermes has native memory (MEMORY.md + episodic SQLite FTS5), smolagents has `agent.memory.steps` (ActionStep/PlanningStep list, programmatically accessible), LangGraph has state checkpoints, a custom agent may not log anything by default. The mechanism is designed to be agnostic via MCP (component F) — but MCP today covers `recall_memory` (read) and `propose_memory_update` (write proposal), not "read the agent's own STM to persist it." Three options surfaced and analyzed 27/08/2026, with a lean recorded:

    - **Opção A — Adapter framework-specific no Write Transform (Rafael's lean for v1 POC).** Quando o evento Kafka chega, o Write Transform identifica qual framework rodou e chama o adapter correto: Hermes adapter lê SQLite FTS5, smolagents adapter lê `agent.memory.steps`, LangGraph adapter lê checkpoints. Cada adapter é pequeno (sabe ler uma estrutura específica — é código, não infra). Zero nova infra, lê de onde já existe. *Pró:* mais viável agora — um adapter pra um framework só na POC, sem precisar definir contrato MCP novo; custo de implementação baixo. *Contra:* N adapters pra N frameworks (cresce linear, mas cada um é pequeno); a lógica de "qual adapter" mora no Write Transform, não no framework.

    - **Opção B — MCP tool `dump_trajectory()` (Rafael's lean como destino/v2).** Padronizado pelo MCP — o mesmo integration layer que o projeto já adota pra `recall_memory` e `propose_memory_update`. Cada squad expõe seu `dump_trajectory()` no seu MCP server, sabendo como ler sua própria STM; o Write Transform chama via MCP sem saber nada de framework-specific. *Pró:* mais elegante — mesmo padrão das outras duas tools, escala do mesmo jeito que o resto da arquitetura, sem adapter central; cada framework é dono de como expõe sua trajetória. *Contra:* cada MCP server precisa implementar a tool nova (mas é uma tool por squad, não um adapter central); precisa definir o contrato/return schema da tool antes de começar.

    - **Opção C — STM única compartilhada (descartada).** Um store padronizado onde todo agente escreve sua STM durante a execução, e o Write Transform lê desse lugar. *Parece* mais simples mas é o mais overengineering de todos: adiciona nova infra (store novo — mesma lógica de "evitar nova dependência operacional" já usada pra descartar git e vector DB dedicado), força instrumentação em cada framework pra escrever nesse store durante a execução, e ou duplica a STM nativa do framework (agente escreve na nativa E na shared) ou substitui a nativa (modifica o framework, quebrando o agnosticismo). Resolve um problema de leitura criando um problema de escrita. **Descartada por Rafael 27/08/2026** — não por preferência, mas por análise: o custo de infra nova + instrumentação + duplicação é estruturalmente maior que ler do que já existe.

    **Lean registrada:** Opção A pra v1 POC (mais viável agora — um adapter, um framework, sem contrato MCP novo pra definir), Opção B como destino (mais elegante — mesmo padrão das outras tools, escala natural com o modelo MCP já adotado). A transição A→B é natural: o adapter vira a implementação behind da tool MCP quando o contrato for definido. Opção C descartada. **Not decided — precisa (a) confirmar na POC que o adapter consegue ler a STM do framework escolhido sem fricção, e (b) definir o return schema de `dump_trajectory()` antes de promove a Opção B de destino a decisão.**
  - **Chunking now matters — a full trajectory is long.** A business-record summary is a few fields; a ReAct trajectory can be dozens of steps. The chunking strategy (gap #4 of the five) now has real teeth: does the score `S` and decay parameters attach to the whole trajectory as one record, or per step? If per step, how are steps from the same case correlated in retrieval? This was previously noted as "not mentioned anywhere in the project corpus" — now it's a live design question, not a hypothetical.
  - **Should there be a promotion gate (SAGE-style) between the episodic log and the LTM, and does it resolve the SAGE-vs-unconditional-ADD tension?** Surfaced 27/08/2026, as a direct consequence of deciding that the episodic trace is the full trajectory (not just the Kafka event). Once the trace is a full ReAct trajectory (~50 steps, ~25KB per stage), logging *everything* into the LTM (indexed, embedded, retrievable via `recall_memory`) is not just costly — it's **contraproducente**: trivial cases (cadastro simples sem erro) dominate the vector space and degrade retrieval signal-to-noise for the agent. A SAGE-style promotion gate (`R = e^(−τ/S)`, θ1/θ2 — already adopted components in this architecture: `S` from DMF-lite, decay from MemoryBank/SAGE) separates two policies for two layers with two purposes:
    - **Episodic log (ADD unconditional):** every trajectory is appended, text-only, no embedding, no indexing. Cheap (~75MB/month at 1000 cases × 3 stages, trivial for any storage). Serves auditability (legal completeness — no case without record) and the Update Engine (needs success *and* failure, reads from the log, not the LTM).
    - **LTM (promotion gated by SAGE):** only trajectories where `R ≥ θ1` get embedded, indexed, and become retrievable via `recall_memory`. Estimated ~20–30% of log volume — the cases that matter enough (by score + recall frequency + time) to be worth retrieving. The other 70–80% stay in the log, consultable but not in the active retrieval space.

    **This resolves the SAGE-vs-unconditional-ADD tension** flagged 25/08/2026 in [`knowledge-as-infra-architecture-hypothesis.md`](knowledge-as-infra-architecture-hypothesis.md#a-memory-store--continuous-non-parametric-per-case) (note at line 66): they were never actually incompatible — SAGE's selectivity applies to *promotion into LTM*, not to *writing the raw log*. The ADD is unconditional for the log (auditability); the gate is selective for the LTM (retrieval quality). Two policies, two layers, two purposes — no conflict. **Rafael's lean 27/08/2026: adopt the gate, not as optional but as structurally necessary** — without it, LTM grows linear with case volume and retrieval drowns in trivial trajectories.

    **Cost analysis by layer (27/08/2026), which drove the lean:**

    | Scale | Traces/month | Log (text, no embedding) | LTM (all, with embedding) | LTM (gated, ~20-30%) |
    |---|---|---|---|---|
    | Piloto beta (~50 cases) | ~150 | ~3.7MB | ~150 embeddings | ~30-50 embeddings |
    | Produção inicial (~1000 cases) | ~3000 | ~75MB | ~3000 embeddings | ~600-1000 |
    | Escala tutor (~6000 cases) | ~18000 | ~450MB | ~18000 embeddings | ~3600-6000 |

    Log grows linear but is cheap (text). LTM without gate grows linear and gets expensive + noisy. With gate, LTM stays ~20-30% of volume — bounded, relevant.

    **What this needs to work (all already in the architecture, no new machinery):**
    - `S` (importance score) — already computed by DMF-lite at write time (component A).
    - Decay formula `R = e^(−τ/S)` — already adopted from MemoryBank (component E).
    - θ1/θ2 thresholds — **new calibration needed** (Sub 1.6/1.7, not portable from SAGE's social-poignancy scale or Generative Agents' "150").
    - `S → S+1` on recall (spacing effect) — already adopted from MemoryBank; reinforces that recall frequency is a real signal for promotion, not just write-time score.

    **Open sub-questions this opens:**
    - **How long does a trajectory sit in the log before the gate evaluates it?** SAGE evaluates on decay over time; but a trajectory that's never recallled has `S` = initial DMF-lite score, decaying from there. Is promotion evaluated on a schedule, on recall, or both? (SAGE: both — items decay continuously, but `S` jumps on recall, which can push `R` back above θ1.)
    - **Does the Update Engine read from the log or the LTM?** Must be the **log** — it needs success *and* failure, and failures (low `S`, never recallled) won't be in the LTM. This is already consistent with the `Store -.-> Engine` edge in the diagram, but sharpens that "Store" here means the episodic log, not the LTM index.
    - **Log retention policy.** The log itself grows — at tutor scale, ~450MB/month, ~10GB over 2 years. Not catastrophic, but needs a retention/archive policy (connects to the hard-delete gated question above — component E applied to the *log*, not just the LTM).
    - **Is the gate's `S` the same DMF-lite score, or a separate "promotion score"?** Reusing the same `S` is simpler and consistent with the architecture's principle of not duplicating signals. But the DMF-lite score was designed for *write-time importance* (how much this case matters), not for *retrieval relevance over time* — these could diverge as design goals.

    **Not decided — but the lean is strong: the gate is structurally necessary, not optional, once the trace is a full trajectory. Needs (a) Sub 1.6/1.7 calibration of θ1/θ2, (b) a decision on when the gate evaluates (schedule vs. on-recall vs. both), and (c) confirmation that the Update Engine reads from the log, not the LTM.**
- **Does the Signal Ledger (component B) need to be a new store, or can it reuse existing platform logging infra — and where does severity live: pre-computed at write time (in the ledger record) or computed on read by the Update Engine?** Surfaced 27/08/2026 working through the trigger mechanism. [`knowledge-as-infra-architecture-hypothesis.md`](knowledge-as-infra-architecture-hypothesis.md#b-signal-capture--dual-path-already-mapped-to-the-platform) draws a Signal Ledger as a separate store from the Memory Store, but its exact schema is already flagged as undefined (component B snapshot). Two sub-questions opened in conversation, both kept open with trade-offs:

  **(1) Reuse vs. build the Signal Ledger:** the systemic path (Yoda/Kafka) already produces logs — the platform may already have a log store for Yoda responses that the mechanism could read from instead of writing into a new dedicated ledger. Reusing would eliminate component B as a separate store and fold it into existing infra — same "avoid a new operational dependency" logic already used to rule out git-as-substrate and a dedicated vector DB. **Blocker:** needs confirmation that Yoda logs are queryable/readable by a new service (not just append-only for dashboards) — a question for the platform team (Fed/Yoshio), not an architecture decision. This question is **orthogonal** to (2) — either severity option works with either a reused or a dedicated store.

  **(2) Where severity lives — two options kept open:**

  - **Opção A — severity pre-computed at write time (stored in the signal record).** Each signal arrives with severity already attributed: `{case_id, signal_type, severity, source, timestamp}`. The Update Engine's trigger check is a cheap sum query over the severity column.
    - *Pro:* trigger check is trivial (sum a column, no reprocessing); severity is attributed at the point closest to the signal source, where context is freshest; closest to Generative Agents' own mechanism (each event already carries its importance score in the memory stream).
    - *Con:* needs a severity-assigning mechanism at write time — straightforward for the copilot path (severity embedded in human feedback: 👎 + reason "wrong deadline" ≠ 👎 + "typo"), but the systemic path has no human to attribute severity at signal time, so a mapping table `outcome_type → severity` or an inference step must run *before* the record is written; if severity logic changes later, old records carry stale values (would need re-processing, same replay argument as component A's transform).

  - **Opção B — severity computed on read by the Update Engine (ledger stays "dumb").** The store logs only the raw signal: `{case_id, signal_type, source, timestamp, ...outcome}`. The Update Engine computes severity from the raw signal when evaluating the trigger, maintaining a cache of the cumulative severity score (push-updated as new signals arrive — the same "push for monitoring, pull for generation" pattern confirmed from Generative Agents).
    - *Pro:* store stays simple and cheap (raw signals only); severity logic is centralized in one place — if the mapping changes, it applies to all historical signals immediately without re-processing stored records; no severity-assigning mechanism needed at the log writer.
    - *Con:* every trigger check needs to interpret the raw signal to compute severity (either reprocess recent signals, or maintain a derived cache that must stay in sync); the severity-mapping logic still needs to exist somewhere — Opção B doesn't eliminate the "who attributes severity in the systemic path" problem, it just moves *where* the answer runs, not *whether* it's needed.

  **Shared dependency for both options:** in the systemic path (Yoda/Kafka), there is no human to attribute severity at signal time. Either a mapping table `outcome_type → severity` is defined (deterministic, auditable — same principle as DMF-lite in component A), or severity is inferred from signal content (costlier, auto-referential — the same risk this design avoids elsewhere). The schema of "what exactly gets captured in systemic mode" is *already* an open gap in the component B snapshot, so severity assignment is a dependency on that, not a new independent question. **Not decided — both options kept open with their trade-offs; needs (a) confirmation that Yoda logs are queryable by a new service [for sub-question 1], and (b) a design for how systemic-mode severity is assigned without a human in the loop [for both options].**

- **Should the Update Engine (component C) have access to a context source beyond the episodic traces it already reads when generating its reflection — and is it the right candidate to also propose harness changes (self-improvement) in a v2?** Surfaced 27/08/2026 working through the engine's role. [`knowledge-as-infra-architecture-hypothesis.md`](knowledge-as-infra-architecture-hypothesis.md#c-update-engine--the-harness-adjustment-layer-batched) confirms the Update Engine reads both the Signal Ledger (which cases were flagged) and the Memory Store's episodic traces (the content of those cases) to run its ExpeL-style comparison. Two sub-questions opened in conversation:

  **(1) Context source for the reflection — v1 question:** the comparison ExpeL-style (success cases vs. failure cases, identify common thread, distill into natural-language insight) currently runs only over the episodic traces the Engine already pulls. Should the reflection step have access to a *second* context source to enrich the analysis? Three candidates surfaced:
  - **Related traces in the same Memory Store** (zero new infra) — the Engine already reads the Store; it could also retrieve traces related to the flagged cases (same keyword, same pipeline stage, same error type) for broader comparison. Risk: echo chamber — the Engine only sees what the platform itself produced, no external "how it should be" reference.
  - **External legal knowledge base** (new infra, new index, latency) — a second RAG over jurisprudence/legislation that the Engine consults to validate whether the insight it's proposing is legally sound, not just empirically consistent with past cases.   - **Business-rule MCP tools already on the platform** (no new infra, already live) — the Engine consults the same MCP tools the agents use (e.g., the "grande causa" threshold tool) to check whether the insight it's proposing doesn't contradict a live business rule.   **(2) Update Engine as the candidate to propose harness changes in v2 — forward-looking, not v1:** today the Update Engine's output is **strategy-layer content only** — it never writes to agent system prompts, never tunes trigger parameters, never touches signal-capture design (per the "Scope clarification: what the Update Engine never touches" section in the architecture doc). - **Should hard-delete be an automatic threshold action, or a gated, reviewed one?** [`knowledge-as-infra-architecture-hypothesis.md`](knowledge-as-infra-architecture-hypothesis.md) draws component E's hard-delete (`R < θ2 → delete + logged reason`) on the hot path, fired automatically by the Memory Store. Alternative raised 27/08/2026 (from reading MemoryBank §2.3, which confirms decay-only forgetting grows storage without bound — see [`../papers/memorybank-2023.md`](../papers/memorybank-2023.md)): the **Memory Store only decays, never deletes**; crossing `θ2` produces a *deletion candidate* that a management component (the Update Engine, or the Consolidation component G) routes through a **human review gate** — "delete this stale item? (Y/N + logged reason)", the Commit Gate pattern reused for removal. Pros: fits tier-1 immutability (deletion is an explicit external logged act, not the store editing itself); compliance signs off on every expiry, not just a threshold crossing. Cons: heavier, slower delete path, another gated flow to run. Also gives the still-hypothetical Consolidation component (G) a concrete remit — dedup **plus** expiry proposals into the same gate. **Not decided.**


- **Which parameters of the v1 architecture should become adaptive (auto-calibrating) in v2, and which rules must remain static (governed)?** Surfaced 27/08/2026 from analyzing the SSGM paper's static/adaptive memory distinction (see [`../papers/ssgm-2026.md`](../papers/ssgm-2026.md)). The v1 architecture is **fully static** — all operations are fixed, auditable, deterministic rules, which is the right choice for the legal/compliance domain (auditability, predictability). The v2 direction records where adaptive *could* enter without undermining the design, governed by one principle: **adaptive can calibrate parameters, never change rules.** The full per-component map is in [`knowledge-as-infra-architecture-hypothesis.md`](knowledge-as-infra-architecture-hypothesis.md#static-vs-adaptive-memory--where-each-component-could-become-adaptive-and-where-it-shouldnt-added-27082026). Summary of the boundary:

  - **Adaptive OK (calibrate parameters):** A (score S weights, SAGE θ1/θ2, decay κ per class), B (outcome_type→severity mapping, path weighting), C (trigger threshold, window size), E (decay κ per class, θ2 candidate threshold, log retention), F (query rewriting, pre-fetching).
  - **Adaptive with caution (improve model, keep rules):** D (NLI model fine-tune — accuracy up, validation rule fixed), C (reflection strategy — black-box risk, needs explainability safeguards).
  - **Adaptive NO (would undermine the design):** D (validation rules, human review requirement, which checks run), B (stopping signal capture — completeness gap), F (MCP interface/contract), E (deleting without gate), C (proposal-not-commit — the Engine always proposes, never commits).

  **Implication for v1 design (not blocking, but shapes implementation):** parameters that are v2-adaptive candidates should be **externalized as config, not hardcoded** in the v1 POC — so they can be learned later without architectural change. This is a design-for-future-adaptability principle, not a v1 requirement. **Not decided — recorded as v2 direction; the v1 POC should externalize these parameters but keep them manually calibrated.**
