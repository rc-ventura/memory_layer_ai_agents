## A note about what "reviewed" means here

**A note existing in `papers/` is not the same as Rafael having read the paper.** Every atomic note in this repo so far — including the ones below — was produced by verifying bibliographic facts (authors, venue, abstract, headline results) against a primary source (arXiv, proceedings page) and writing a summary from that. That is real verification work, and it's useful: it catches fake citations, wrong venues, mismatched titles. But it is **not** the close reading that produces the kind of understanding Rafael needs to defend this material to [TUTOR] or make an architecture call on top of it.

So: nothing in this file is "done" in the reading sense until Rafael says he read it. The checklist below reflects that — every item is unchecked, regardless of whether a note already exists.

**How to verify:** never fabricate an arXiv ID, author list, or date. `arxiv.org` direct fetch (`WebFetch`) is blocked by this environment's network egress — use `WebSearch` instead to confirm title/authors/date/headline claims; it's been reliable for this. Always keep "verified" (bibliographic facts checked) and "read" (Rafael actually read it) distinct — never conflate the two.

**A third tier, added 24/08/2026:** 🔎 = an agent (no defined provider) read the **full text** (not just the abstract) via a dispatched sub-agent, and extracted specific mechanisms/formulas/answers to a gating question. Stronger than 📝 (bibliographic verification only), but still **not** the same as ✅ (Rafael read it) — don't collapse this into "read" in any deliverable. Full findings: [`../discussion/reading-sprint-2026-08-24-queue-papers.md`](../discussion/reading-sprint-2026-08-24-queue-papers.md).

- [ ] **15. Evo-Harness** (arXiv:2608.15071) — **"Context-to-Harness Skill Compilation for Self-Evolving Agents"**. - [ ] **16. TrajTune** (ICLR 2026, OpenReview) — **"Trajectory-Based Prompt Optimization for LLM Agents"**. - [ ] **17. Recuris** (arXiv:2608.24876) — **"Recursive Experiential–Working Memory Evolution for Long-Horizon Agent Harnesses"**. - [ ] **18. Self-Correction Illusion** (arXiv:2606.05976) — **"LLMs Correct Others but Not Themselves"**. Achado crítico pro design do Update Engine: LLMs não se autocorrigem quando o claim está no próprio `<thought>`, mas corrigem 23-93pp mais quando o mesmo claim aparece como `<user>` ou `<memory>`. É artifact do chat-template, não déficit cognitivo. **Implicação direta:** se o Update Engine lê suas próprias insights passadas como `<thought>`, pode não corrigi-las bem; se as reenquadra como externas (via `recall_memory` como tool call, que retorna como `<tool>`), consegue. Reforça o risco de auto-referência que o design já evita no score DMF-lite (componente A) — e sugere que o Update Engine deveria ler insights passadas como conteúdo recuperado, não como memória interna. Vale ler pra: (a) fundamentar empiricamente por que o Update Engine não deve operar sobre suas próprias outputs auto-referencialmente, (b) o `<memory>` role-label como candidato a como entregar insights recuperadas ao agente.

Introduz o **Agent Stability Index (ASI)** — métrica composta em 12 dimensões (consistência de resposta, padrões de uso de tool, estabilidade do caminho de raciocínio, taxa de concordância entre agentes…). **Por que interessa:** (a) dá nome e taxonomia ao "semantic drift" que o Commit Gate (D) e a reconciliação (E) existem pra conter — bate direto com a família *Stability* da taxonomia de erros do SSGM; (b) o **ASI é candidato concreto a operacionalizar a métrica "estabilidade" do Sub 3.6** (hoje só nomeada, sem definição), com várias das 12 dimensões mensuráveis direto nos traces. **Ressalvas:** é multi-agente e mede drift *dentro* de execuções longas; o nosso caso é agente de tarefa curta + cross-trial — nem toda dimensão transfere, e **coordination drift é fora de escopo** (os agentes da esteira não conversam entre si).

**Fora do checklist ativo, por design:** GraphRAG/G-Memory/LegalGraphRAG (bloqueados por Sub 1.4 — ver [condicional](#priority-reading-list--rodada-2-19082026) e a entrada do LegalGraphRAG na seção logo abaixo), o survey de forgetting fev/2026 e o catálogo de políticas dez/2025 (sem arXiv ID confirmado ainda), e GITM (já descartado — ver [downgraded](#downgraded--deprioritized-18082026-session)).

Directly operationalizes the exact short/long-term + episodic/semantic taxonomy named in the project's own Sub 1.1 description — and it's a sixth RL flavor the corpus didn't have yet: RL over **tier-routing decisions** (which store a memory goes to), distinct from RMM (retrieval reranking), Memory-R1 (write operations), Retroformer (prompt adaptation), and Mem-α (target unconfirmed). Code: github.com/humemai/explicit-memory. First surfaced by Rafael from a citation inside 2512.13564 ("Room," Kim et al., 2023b) that needed the full reference before it could be identified — resolved 20/08/2026.
- **Westhäußer, Minker, Zepf — "Enabling Personalized Long-term Interactions in LLM-based Agents through Persistent Memory and User Profiles"** (2025, arXiv:2510.07925). A framework integrating persistent memory, dynamic coordination, self-validation, and evolving user profiles for personalized long-term agent interactions. Cited by 2512.13564 under both "long-horizon/life-long agents" and "user-specific personalization" — relevant to the project's persistence-across-sessions requirement, but not urgent since no specific open question is riding on it.

## Surfaced from legal-domain / governance search, tied to the architecture hypothesis (25/08/2026)

Found while searching for a paper implementing a memory-update mechanism specifically in legal or another specialized-knowledge workflow — see [`../discussion/knowledge-as-infra-architecture-hypothesis.md`](../discussion/knowledge-as-infra-architecture-hypothesis.md). All three were read in full (by an agent, via direct PDF download + `pdftotext`, not Rafael-read) the same day they were found — 🔎 tier throughout. SSGM and "When Rules Learn" were promoted into the main numbered checklist above (Tier 1, #1 and #6, 25/08/2026) — full detail kept here. LegalGraphRAG stays unnumbered/conditional, grouped with GraphRAG/G-Memory.

- **"Governing Evolving Memory in LLM Agents... (SSGM Framework)"** (Lam, Li, Zhang, Zhao, Mar 2026, arXiv:2603.11768) 🔎 — not legal-specific, but the strongest single addition to the architecture found so far: a formal Write Validation Gate (Truth Maintenance System, NLI contradiction check `ΔM ∧ M_core ⊨ ⊥`) for the Commit Gate; a Weibull decay function `w(Δτ)=exp(−(Δτ/η)^κ)` for Forgetting, more expressive than MemoryBank's plain exponential; and a "Reversible Reconciliation" principle (immutable episodic log + mutable derived graph, replayable) that gives Sub 3.4's rollback requirement a real mechanism instead of an unspecified one. See the architecture note's updated components D/E for how this gets folded in.
- **"When Rules Learn: A Self-Evolving Agent for Legal Case Retrieval"** (ACL 2026, arXiv:2606.17220) 🔎 — a real legal-domain precedent for rule elimination (two-stage self-consistency voting, `n=7` trials, `δ=0.5`), but its reward is fully automatic (Recall@k against a benchmark) and elimination is the *same* LLM voting on its own rules — no external/human signal anywhere. Doesn't validate our Commit Gate design; it's a live example of exactly the correlated-error risk Casper et al. warns about (see [`../discussion/thumbs-feedback-reliability.md`](../discussion/thumbs-feedback-reliability.md)) — worth citing as a cautionary real-world case, not an architecture source.
- **"LegalGraphRAG: Multi-Agent Graph Retrieval-Augmented Generation for Reliable Legal Reasoning"** (ACL 2026, arXiv:2605.28120) 🔎 — less relevant than the abstract suggested: builds its hierarchical legal graph **offline from a static corpus**, no incremental update, no forgetting — it's a sophisticated retrieval+verification system (Researcher/Auditor/Adjudicator), not a memory-update mechanism. Doesn't confirm or refute the cross-trial/forgetting design since it doesn't attempt that. Only relevant if graph-structured retrieval gets adopted later (see the GraphRAG note above) — as a pattern for hierarchical structure + a retrieval-time verify-and-prune step, not for components C/D/E.
