# SSGM: Governing Evolving Memory in LLM Agents

- **Authors:** Lam, Li, Zhang, Zhao
- **Year:** 2026
- **Venue:** arXiv:2603.11768 (March 2026)
- **Link:** https://arxiv.org/abs/2603.11768
- **Tags:** governance, forgetting, weibull, reversible-reconciliation, write-validation, adaptive-memory, priority-read

## Core contribution

A framework for governing evolving memory in LLM agents, organized as a three-layer conceptual architecture (Figure 4):

1. **Cognition Layer** — the LLM agent that interacts with the environment and produces memory operations.
2. **Governance Middleware** — intercepts memory interactions between the agent and the substrate. Two pathways:
   - **Upper (Write Validation):** governs memory consolidation via a Truth Maintenance System (TMS) that rejects a candidate update `ΔM` when `ΔM ∧ M_core ⊨ ⊥` (NLI-based contradiction check against protected core facts).
   - **Lower (Read Filtering):** governs memory retrieval by enforcing access scopes (ACL/ABAC) and temporal relevance.
3. **Memory Substrate** — dual-memory: a **mutable active graph** (derived, replayable) paired with an **immutable episodic log** (source of truth). This pairing supports **Reversible Reconciliation**: recover from drift or a bad commit by replaying the mutable layer from the immutable log, rather than maintaining hand-rolled diffs.

Key mechanisms formalized:
- **Weibull decay:** `w(Δτ) = exp(−(Δτ/η)^κ)` — more expressive than MemoryBank's plain exponential; the shape parameter `κ` lets decay be fast-then-flat or slow-then-steep, tunable per memory class.
- **Write Validation Gate:** TMS-based contradiction check, more rigorous than Mem0's simpler `Contradicts(f, M) → DELETE`.
- **Reversible Reconciliation:** immutable log + mutable derived layer = rollback by replay, not by hand-rolled version history.

The paper also frames a distinction between **static memory systems** (Generative Agents, MemoryBank — content changes but operations are fixed rules) and **adaptive memory systems** (MemGPT, Memory-R1 — the operations themselves are learned policies that adapt with experience). See the section below for how this project's architecture positions itself on this axis.

## Relevance to the project

SSGM is Tier 1 #1 in the [reading queue](reading-queue.md) — the single highest-priority read. It formally grounds three components of the architecture hypothesis that no other paper in the corpus covers:

- **Commit Gate (component D, Governance Layer):** the Write Validation Gate / TMS-NLI contradiction check is the formalism behind the project's actual contribution — the piece none of the eight read papers have.
- **Forgetting (component E):** the Weibull decay formula is more expressive than MemoryBank's exponential, and the "pruned... before reaching the agent's context window" language is closer to real deletion than MemoryBank's rank-deprioritization-only behavior.
- **Rollback (Sub 3.4):** Reversible Reconciliation gives the rollback requirement a real mechanism (replay mutable from immutable) instead of an unspecified "keep version history."

The architecture hypothesis adopted the SSGM three-layer structure (Cognition → Governance → Memory) with one key adaptation: SSGM centralizes governance in a single middleware that intercepts *all* memory interactions; this project distributes governance to the points where it's needed — Commit Gate only on strategy-layer writes (cold path), ACL/freshness filtering inside `recall_memory` (read path), and the episodic log is ADD-unconditional (no gate, by legal auditability requirement). Same governance pattern, distributed instead of centralized. See the [SSGM layer mapping](../discussion/knowledge-as-infra-architecture-hypothesis.md#ssgm-layer-mapping-added-27082026) in the architecture doc.

## Static vs. adaptive memory — where this project's architecture sits (added 27/08/2026)

SSGM frames a distinction that positions this project's architecture explicitly:

**Static memory systems** (SSGM's framing: Generative Agents, MemoryBank): the *content* of memory changes with experience, but the *operations* (write rules, retrieval formula, decay formula, trigger logic) are **fixed** — they don't learn, they don't adapt. MemoryBank always uses the same Ebbinghaus formula; Generative Agents always uses the same recency+importance+relevance scoring. The mechanism is the same regardless of how much experience has accumulated.

**Adaptive memory systems** (SSGM's framing: MemGPT, Memory-R1, Memo): the *operations themselves* are **learned policies** that adapt with experience. Memory-R1 learns via RL when to ADD/UPDATE/DELETE/NOOP — the operation is a trained policy, not a fixed rule. MemGPT adapts how it compresses — what to preserve vs. discard changes with context. The "how" of memory learns, not just the "what."

**Where this project's architecture sits: STATIC, by design.** Mapping each operation:

| Operation | Fixed or learned? | Category |
|---|---|---|
| Write to episodic log (ADD unconditional) | Fixed — always, no exception | Static |
| Score `S` at write time (DMF-lite) | Fixed — deterministic formula | Static |
| Decay `R = e^(−Δt/S)` / Weibull | Fixed — same formula, θ1/θ2 calibrated manually | Static |
| Retrieval (`recall_memory`: top-K + ACL + freshness + relevance) | Fixed — same formula always | Static |
| SAGE gate (promotion log→LTM) | Fixed — θ1/θ2 are calibrated, not learned | Static |
| Update Engine reflection (ExpeL-style) | Fixed — always compares success vs. failure | Static |
| Commit Gate checks (NLI, signal quality) | Fixed — same checks always | Static |
| **Content** of strategy layer | Adapts — changes based on signals | — |

All operations are fixed, auditable, deterministic rules. The content adapts; the mechanism doesn't. This is static memory in SSGM's sense.

**Why static is the right choice for this domain (legal/compliance/Itaú):**

| | Adaptive (Memory-R1, MemGPT) | Static (this design) |
|---|---|---|
| **Auditability** | Low — learned policy is a black box, can't explain why ADD vs. UPDATE | **High** — every operation is an explainable, deterministic rule |
| **Predictability** | Low — same input can produce different behavior at different times | **High** — same input always produces same decision |
| **Legal compliance** | Problematic — "why did the system forget this case?" has no deterministic answer | **Natural** — "decayed below θ2 per Ebbinghaus formula, gate approved deletion" |
| **Flexibility** | High — adapts to new patterns automatically | Limited — needs manual recalibration of θ1/θ2 |

The Commit Gate exists *precisely* to ensure every change is human-reviewed and versioned — if the memory policy itself were learned (adaptive), that control would be undermined. Static is not a limitation here; it's a deliberate design choice coherent with the domain.

**What differentiates this design from other static systems** (MemoryBank, Generative Agents — also static) is not the static/adaptive axis. It's the **controlled/uncontrolled** axis: this design has governance on strategy-layer writes (Commit Gate) that the other static systems don't have. The novelty is in the control layer, not in the learning layer.

**v2 direction — where adaptive could enter, cautiously:** the Update Engine v2 (proposing harness changes, recorded 27/08/2026 in [`open-questions.md`](../discussion/open-questions.md)) is where the mechanism *could* become more adaptive — thresholds θ1/θ2 could auto-calibrate, the Engine could learn which reflection patterns produce better insights. But even in v2, the governance layer (Commit Gate) should remain static/deterministic — what learns is the *calibration* of parameters, not the *rules* of validation. Adaptive calibration, static governance.
