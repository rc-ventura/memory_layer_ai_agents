# SSGM: Governing Evolving Memory in LLM Agents

- **Authors:** Chingkwun Lam, Jiaxin Li, Lingfei Zhang, Kuo Zhao (Jinan University)
- **Year:** 2026
- **Venue:** arXiv:2603.11768 (12 March 2026) — preprint, no venue confirmed
- **Link:** https://arxiv.org/abs/2603.11768
- **Code / artifacts:** **none — by design.** Checked 31/08/2026 (WebSearch × 3 + the paper's own HTML on ar5iv/arxiv-html): no GitHub, no project page, no released implementation, no reproducible experiments. The paper states explicitly: *"Rather than a specific software implementation, SSGM provides a rigorous theoretical architecture and a set of design principles."* It's a position/framework paper — formal analysis (equations, decay/gate formalism), architectural decomposition, taxonomies, and testable hypotheses for future evaluation. So there is no reference implementation to port: the project has to implement the Weibull decay, the TMS/NLI Write Validation Gate, and Reversible Reconciliation itself, taking SSGM as the spec, not the codebase.
- **Tags:** governance, forgetting, weibull, reversible-reconciliation, write-validation, adaptive-memory, priority-read, evolution-taxonomy, content-structure-policy, forgetting-by-design, fifa-benchmark, reflection, e-mem, graph-rag, error-taxonomy, no-code-conceptual-framework

## Core contribution

A framework for governing evolving memory in LLM agents, organized as a three-layer conceptual architecture (Figure 4):

1. **Cognition Layer** — the LLM agent that interacts with the environment and produces memory operations.
2. **Governance Middleware** — intercepts memory interactions between the agent and the substrate. Two pathways:
   - **Upper (Write Validation):** governs memory consolidation via a Truth Maintenance System (TMS) that rejects a candidate update `ΔM` when `ΔM ∧ M_core ⊨ ⊥` (NLI-based contradiction check against protected core facts).
   - **Lower (Read Filtering):** governs memory retrieval by enforcing **cryptographic provenance** (the unit was produced by a trusted source), access scopes (ACL/ABAC), and temporal relevance (Weibull freshness). See Principle 2 below.
3. **Memory Substrate** — dual-memory: a **mutable active graph** (derived, replayable) paired with an **immutable episodic log** (source of truth). This pairing supports **Reversible Reconciliation**: recover from drift or a bad commit by replaying the mutable layer from the immutable log, rather than maintaining hand-rolled diffs.

Key mechanisms formalized:
- **Weibull decay:** `w(Δτ) = exp(−(Δτ/η)^κ)` — more expressive than MemoryBank's plain exponential; the shape parameter `κ` lets decay be fast-then-flat or slow-then-steep, tunable per memory class.
- **Write Validation Gate:** TMS-based contradiction check, more rigorous than Mem0's simpler `Contradicts(f, M) → DELETE`.
- **Reversible Reconciliation:** immutable log + mutable derived layer = rollback by replay, not by hand-rolled version history.

The paper also frames a distinction between **static memory systems** (Generative Agents, MemoryBank — content changes but operations are fixed rules) and **adaptive memory systems** (MemGPT, Memory-R1 — the operations themselves are learned policies that adapt with experience). See the section below for how this project's architecture positions itself on this axis.

## SSGM's design principles — P1–P4 (added 31/08/2026, Rafael reading)

SSGM frames its architecture as a set of principles. Rafael has read through P4 as of 31/08/2026 (the paper may have further principles; not yet read).

### Principle 1 — Pre-Consolidation Validation

No memory update is committed passively. Biological analogy the paper draws: the hippocampus doesn't instantly commit every perception to the neocortex — information is filtered and reality-monitored first (Tresp et al., 2023, as cited by SSGM). In SSGM, when the agent produces a memory delta `∆M`, it must clear the **Write Validation Gate** (the upper consolidation pathway, Figure 4):

- The gate acts as a **Truth Maintenance System (TMS)**: it retrieves established core facts `M_core` and runs a strict logical-contradiction check — if `∆M ∧ M_core ⊨ ⊥` evaluates true, the update is **rejected**.
- **The gate is trigger-agnostic.** Whatever produces `∆M` — an agent's RL-learned decision to ADD, an end-of-subtask / end-of-task hook, an N-turn-cycle timer, an error/failure detection, a generated reflection — the write is intercepted *before* it commits. SSGM decouples *what triggers a write* from *how a write is validated*; they are separate design questions. (For this project the **write-phase trigger is still open** — episodic-write granularity per-stage vs. per-subtask vs. per-N-turns vs. per-case, tracked in [`../discussion/open-questions.md`](../discussion/open-questions.md); Update-Engine/strategy-write trigger = severity / schedule / human, per the 28/08 checkpoint.)
- The contradiction check uses **formal Natural Language Inference (NLI)** (SSGM cites Xu et al., 2025). SSGM does **not** state *how* NLI is implemented. **Rafael's reading leans "a classic ML classifier"** — premise + hypothesis → {entailment / neutral / contradiction} — not a generative LLM. **For this project this stays an explicit open gap:** the Commit Gate (component D) could use a dedicated NLI classifier (fast, cheap, deterministic-ish, auditable against a fixed benchmark) *or* an LLM prompted to judge contradiction (more flexible for subtle legal nuance, but slower, token-costly, and reintroduces the self-referential-judgment risk the design otherwise avoids). See [`../discussion/knowledge-as-infra-architecture-hypothesis.md`](../discussion/knowledge-as-infra-architecture-hypothesis.md) → "Two open implementation gaps in the Commit Gate".
- Purpose: stop **hallucination cascades** from permanently corrupting the semantic graph — an error consolidated once compounds on every later summarization pass.
- **Link to Reversible Reconciliation:** P1 is *why* the memory layer keeps the **raw episodic log immutable**. Summarization and iterative rewriting lose important passages from earlier runs, so reconciliation — recovering from drift or a bad commit — is run **directly against the raw log**, not against a chain of summaries.

**For this project:** P1 is the formalism behind the Commit Gate (component D). But note the project's *distributed* adaptation — the gate runs **only on strategy-layer writes** (cold path, batched, rare), never on every episodic write (ADD-unconditional, for legal auditability). Combined with the trigger-agnostic point above, this means the two questions separate cleanly: the strategy-write's *trigger* can be anything (severity, schedule, human, error-detection, reflection) and the gate doesn't care which — it validates the resulting `∆M` the same way regardless. The episodic write, by contrast, has a **fixed system trigger and no gate**. So the NLI cost is **per batch, not per case** (cost discussion in the architecture doc).

### Principle 2 — Read Filtering (trusted, fresh sources only)

The agent never retrieves memory straight into its prompt. Before any candidate memory unit is injected into the agent's context, it passes the **Read Filtering Gate** (the lower retrieval pathway, Figure 4), in two stages:

1. **Cryptographic provenance check** — the system verifies the memory unit was generated by a **trusted source** (a provenance signature attached to the unit). Units without valid provenance are filtered out before ranking.
2. **Weibull freshness check** — the decay function `w(Δτ) = exp(−(Δτ/η)^κ)` is evaluated; if the unit's freshness has fallen **below the threshold** `θfresh`, it is **pruned** (not surfaced to the agent), even when it's a strong semantic match.

Units that clear both → enter the agent's context. Units that fail either → pruned.

**For this project:** P2 is the formalism behind `recall_memory`'s retrieval mechanics (component A2), already adopted as `Ct = {μ ∈ Top-K(qt, Mt-1) | ACL(μ, uid) ∧ (w(Δτμ) ≥ θfresh)}`. Two notes:
- The **provenance** dimension is **not yet unpacked** for this project — it overlaps the open `ACL(μ, uid)` gap ([`../discussion/open-questions.md`](../discussion/open-questions.md)) and is the same idea as **Collaborative Memory**'s (arXiv:2505.18279, [`reading-queue.md`](reading-queue.md) #44) "immutable provenance attributes for retrospective permission checks". For legal auditability, provenance — *which agent, which run, from which source* produced a memory unit — is arguably non-negotiable, not optional.
- The Weibull check here is a **read-time** filter, distinct from the **promotion-time** `R ≥ θ1` gate ([`../discussion/promotion-policy-log-to-ltm.md`](../discussion/promotion-policy-log-to-ltm.md)). Same decay function, two checkpoints: one decides what *enters* the retrievable LTM, the other decides what a given query *surfaces*.

### Principle 3 — Scoped Access (RBAC / identity-bound retrieval)

Access to the memory layer is **scoped**, not global. The Read Filtering Gate **binds the caller's identity into every retrieval** — the query carries *who* is asking (which agent, which execution, which role), and the gate returns only the memory units that identity is authorized to see. This is **RBAC** (role-based access control) / the **ABAC principle** already noted in the Core contribution — access decided from attributes of requester and unit, not a fixed list. It is the `ACL(μ, uid)` term of the retrieval formula, made concrete.

Together, **P2 + P3 fully define the Read Filtering Gate**: a candidate memory unit must clear all three checks to reach the agent's context — **provenance** (trusted origin, P2) + **access scope** (identity authorized, P3) + **freshness** (Weibull threshold, P2).

**For this project:**
- P3 maps directly onto the project's lean, endorsed by the tutor on 28/08: **domain-scoped access + credentials/RBAC**, the agent passing a domain, **per-squad rather than per-case** (Rafael's "mega brain with granularity"). In that sense P3 is "what the project already wants to do" — but it is a **lean, not a done thing**: the 21/08 infra meeting confirmed there is **no centralized auth today** (user token propagated layer to layer, each app validating independently), so the actual mechanism — what carries the identity into a memory read, which attributes scope it, whether there's an LGPD dimension beyond domain — is still the open `ACL(μ, uid)` gap ([`../discussion/open-questions.md`](../discussion/open-questions.md)).
- **Collaborative Memory** (Rezazadeh et al., arXiv:2505.18279 — [`reading-queue.md`](reading-queue.md) #44) is the candidate *implementation* of P3: a dynamic, asymmetric, time-evolving access model (bipartite user×agent×resource graph, private/shared tiers, immutable provenance for retrospective checks). Adaptation for this project: "user" → domain/squad. It also gives the **task-private vs. cross-agent-reusable** memory-class split ([`../discussion/open-questions.md`](../discussion/open-questions.md)) a concrete enforcement mechanism — private fragments = one agent-type's *modus operandi*, shared fragments = the reusable operational pool.

### Principle 4 — Dual structure + asynchronous reconciliation

The memory substrate is **split in two**: a **semantic layer** (mutable, derived) and an **episodic / raw interaction trace** (immutable, source of truth). This dual structure enables **asynchronous reconciliation** — the system periodically **"replays"** and corrects drifted concepts against the raw interaction trace, "effectively offering a rollback mechanism if severe agent behavioral degradation occurs" (Rath, 2026 — [`reading-queue.md`](reading-queue.md) #45). This is the **Reversible Reconciliation** mechanism already listed under Core contribution and Key mechanisms, stated here as a principle: don't maintain hand-rolled diffs; recover by replaying the derived layer from the immutable log.

- **(Rath, 2026)** is SSGM's citation for the *problem* P4 guards against — "Agent Drift" (arXiv:2601.04170): progressive behavioral degradation over extended interactions, with **semantic drift** (deviation from original intent) as one of three named forms, plus the **Agent Stability Index (ASI)**, a 12-dimension composite metric. Added to the reading queue (#45); relevant to component E, Sub 3.4 (rollback), and Sub 3.6 (the ASI is a concrete candidate for operationalizing "estabilidade", today only named). *Name discrepancy: SSGM's reference list spells the author "Abhinav Rath"; arXiv's own author line says "Abhishek Rath".*

**For this project:** P4 is the formalism behind Sub 3.4's rollback requirement and component E's replay design — already adopted. The project's two-layer split (immutable episodic log + mutable strategy layer) *is* P4's dual structure. What P4 adds beyond "keep version history" is the **replay-from-raw-trace** recovery path: a bad Commit Gate approval or accumulated drift is undone by re-deriving the strategy layer from the immutable log, not by reverting diffs. The "asynchronous" part maps onto the cold path — reconciliation is a batched, scheduled operation, not per-case.

### The reconciliation operator and Theorem 1 (Bounded Semantic Drift) — added 01/09/2026, Rafael reading

P4's "asynchronous reconciliation" is given a formal objective (Eq. 7) and a stability theorem (Theorem 1). This subsection is **the article's own mechanism**, kept separate from any adaptation this project builds on top of it.

**Three reference objects, three roles** — SSGM states this explicitly to stop them being conflated:

| Object | Role | Where it acts |
|---|---|---|
| `M_core` | protects critical facts | at **write** — the Write Validation Gate rejects `ΔM` when `ΔM ∧ M_core ⊨ ⊥` |
| `K_ledger` | the operational **raw trace**, used **for correction** | during **reconciliation** — `R` replays / corrects against it |
| `K_true` | the **ideal** semantic target, used **for evaluation** | only inside the objective — not an object the system holds in production |

**Drift measure `δ(·,·)`** (Eq. 4): a semantic-distance function between two knowledge states — meaning-level divergence, not textual diff. (Eq. 4's exact form is not captured in this note — flag for a closer read.)

**Reconciliation objective** (Eq. 7):

```
M_clean  ←  arg min_M   E[ δ( R(M, K_ledger) , K_true ) ]
```

`R(M, K_ledger)` is the memory obtained by replaying or correcting a candidate state `M` using the immutable ledger. The system searches for the cleaned state whose *reconciled form* is, in expectation (over stochastic trajectories, noisy summaries, noisy reconciliation decisions), closest to the ideal `K_true`. Note the objective measures distance to `K_true`, **not** directly to `K_ledger` — the raw ledger is the material `R` rebuilds from; `K_true` is the target the rebuild should approximate.

**Theorem 1 (Bounded Semantic Drift).** Assumptions: (a) each valid summarization / consolidation step introduces at most `ε_step` of semantic error before reconciliation; (b) `R` restores the mutable memory to a state whose *residual* error is bounded by a constant independent of the horizon `T`. Then:

- **Naive system** (no Eq. 7): per-step errors accumulate additively → expected drift at `T` is `O(T · ε_step)` — unbounded in the horizon.
- **SSGM**, reconciliation every `N` steps: expected drift is upper-bounded by `O(N · ε_step)` — bounded by the **window size `N`**, not the horizon. Stable even when `T ≫ N`.

*Proof sketch:* unconstrained, `E[δ(M_T)] ≤ Σ_{t=1..T} ε_step = T · ε_step`. Under SSGM, error accumulates for at most one reconciliation window before correction: for `T = mN + r` with `0 ≤ r < N`, the un-reconciled portion contributes at most `r · ε_step < N · ε_step`, plus the bounded residual reconciliation error. The dominant growth term is `N`, not `T`.

**What the theorem does and doesn't give:**
- An **expected-drift bound** (not worst-case), and only a **proof sketch**.
- It converts unbounded `O(T)` drift into bounded `O(N)` drift **only if both assumptions hold**: `ε_step` is bounded — which presumes the Write Validation Gate actually catches the large-error class, so `ε_step` is the *residual after gating* — and `R` is genuinely effective and does not itself degrade over time.
- It assumes **additive** accumulation; a distorted summary feeding the next summarization could compound worse than additively. The theorem takes the optimistic model.
- `N` is a **design knob**: smaller `N` = tighter drift bound but more frequent (and, if `R` uses an LLM to re-derive, more expensive) passes; larger `N` = cheaper, looser bound. "At most one window of un-corrected error present at any time" is exactly the guarantee — reconciliation runs every `N` steps, **not** every update.

**For this project:** Theorem 1 is the formal reason the *reconciliation cadence* is a parameter to calibrate, not an afterthought — it sets the drift the strategy layer can carry between passes (connects to the open "evaluation cadence" item in [`../discussion/open-questions.md`](../discussion/open-questions.md) and the cold-path batching). `K_true` ≈ the manually annotated gold standard the project does not have yet (Sub 3.6 Reference Accuracy, blocked on Sub 1.4 + 1.5); until it exists, a real reconciliation pass can only approximate the objective — re-derive from the log, check internal + `M_core` consistency. And `ε_step` is only bounded if the Commit Gate (component D) actually catches the contradiction class it targets — the stability guarantee is downstream of the gate working.

## Static vs. adaptive memory — where this project's architecture sits (added 27/08/2026)

SSGM frames a distinction that positions this project's architecture explicitly:

**Static memory systems** (SSGM's framing: Generative Agents, MemoryBank): the *content* of memory changes with experience, but the *operations* (write rules, retrieval formula, decay formula, trigger logic) are **fixed** — they don't learn, they don't adapt. MemoryBank always uses the same Ebbinghaus formula; Generative Agents always uses the same recency+importance+relevance scoring. The mechanism is the same regardless of how much experience has accumulated.

**Adaptive memory systems** (SSGM's framing: MemGPT, Memory-R1, Memo): the *operations themselves* are **learned policies** that adapt with experience. Memory-R1 learns via RL when to ADD/UPDATE/DELETE/NOOP — the operation is a trained policy, not a fixed rule. MemGPT adapts how it compresses — what to preserve vs. discard changes with context. The "how" of memory learns, not just the "what."

**Where this project's architecture sits: STATIC, by design.** Mapping each operation:

| Operation | Fixed or learned? | Category |
|---|---|---|
| Write to episodic log (ADD unconditional) | Fixed — always, no exception | Static |
| Score `S` at write time (DMF-lite) | Fixed — deterministic formula | Static |
| Decay `R = e^(−Δt/S)` / Weibull | Fixed — same formula, θ1/θ2 calibrated manually | Static |
| Retrieval (`recall_memory`: top-K + ACL + freshness + relevance) | Fixed — same formula always | Static |
| SAGE gate (promotion log→LTM) | Fixed — θ1/θ2 are calibrated, not learned | Static |
| Update Engine reflection (ExpeL-style) | Fixed — always compares success vs. failure | Static |
| Commit Gate checks (NLI, signal quality) | Fixed — same checks always | Static |
| **Content** of strategy layer | Adapts — changes based on signals | — |

All operations are fixed, auditable, deterministic rules. The content adapts; the mechanism doesn't. This is static memory in SSGM's sense.

**Why static is the right choice for this domain (legal/compliance/Itaú):**

| | Adaptive (Memory-R1, MemGPT) | Static (this design) |
|---|---|---|
| **Auditability** | Low — learned policy is a black box, can't explain why ADD vs. UPDATE | **High** — every operation is an explainable, deterministic rule |
| **Predictability** | Low — same input can produce different behavior at different times | **High** — same input always produces same decision |
| **Legal compliance** | Problematic — "why did the system forget this case?" has no deterministic answer | **Natural** — "decayed below θ2 per Ebbinghaus formula, gate approved deletion" |
| **Flexibility** | High — adapts to new patterns automatically | Limited — needs manual recalibration of θ1/θ2 |

The Commit Gate exists *precisely* to ensure every change is human-reviewed and versioned — if the memory policy itself were learned (adaptive), that control would be undermined. Static is not a limitation here; it's a deliberate design choice coherent with the domain.

**What differentiates this design from other static systems** (MemoryBank, Generative Agents — also static) is not the static/adaptive axis. It's the **controlled/uncontrolled** axis: this design has governance on strategy-layer writes (Commit Gate) that the other static systems don't have. The novelty is in the control layer, not in the learning layer.

**v2 direction — where adaptive could enter, cautiously:** the Update Engine v2 (proposing harness changes, recorded 27/08/2026 in [`open-questions.md`](../discussion/open-questions.md)) is where the mechanism *could* become more adaptive — thresholds θ1/θ2 could auto-calibrate, the Engine could learn which reflection patterns produce better insights. But even in v2, the governance layer (Commit Gate) should remain static/deterministic — what learns is the *calibration* of parameters, not the *rules* of validation. Adaptive calibration, static governance.

## SSGM's taxonomy of memory evolution — content, structure, policy (added 31/08/2026, Rafael reading)

SSGM's central framing is that the field is shifting from **static** memory (a store that just holds text) toward **adaptive** memory (a store that changes itself over time), and it decomposes *how* a memory system evolves along **three axes**. SSGM cites a cluster of systems moving this way — MemGPT, Memory-R1, MemAct, Nemori, AdaMem, MemCon, FLUXMEM, Rosetta Memory, AWM (all catalogued in [`reading-queue.md`](reading-queue.md) under "Adaptive memory references" and "Memory structure evolution", added 27/08/2026). This project stays deliberately static — see the section above for the positioning; below is SSGM's descriptive taxonomy.

### 1. Evolving the **content**

Static storage just holds facts as written. Adaptive content is continually rewritten, so the KB becomes a **dynamic artifact that changes over time**. The most common technique on this axis is **summarization / abstraction** — condensing raw records into higher-level statements. SSGM's key finding here:

> *"This shift from purely textual facts to procedural content increases the complexity of maintaining consistency, as errors in procedural memory can lead to cascading failures in task execution."*

**For this project:** a direct argument for the two-layer split — the immutable episodic log stays raw (no cascading-error surface), and abstraction/summarization only happens in the *derived* strategy layer, which is exactly where the Commit Gate's consistency checks (NLI contradiction against `M_core`) sit. It also sharpens why the strategy layer holds *procedural/strategy* content, not just facts — and why that content specifically is what needs the gate.

### 2. Evolving the **structure**

How the KB is *organized* directly determines retrieval efficiency. SSGM reports that structural-evolution techniques nearly all reduce to the same idea: **maintain links between related facts** — build a linked or hierarchical structure that grows dynamically, rather than storing traces as isolated, unconnected records. This is why **Graph RAG**-style approaches are relevant: memory shouldn't be a flat pile of independent traces; related items should carry relations to each other.

**For this project:** the strongest external push so far toward reconsidering the v1 "flat text 1D, no graph" decision for component A — but it stays **gated on Sub 1.4** (does the target legal flow actually need multi-hop navigation between precedents?), consistent with the existing GraphRAG / Mem0g / HippoRAG gate in [`reading-queue.md`](reading-queue.md). Recorded, not adopted.

### 3. Evolving the **policy**

The *policy* is how memory is managed (when to write / update / delete / retrieve). SSGM splits the work here into:

- **RL-with-rewards** — the operation is a trained policy (Memory-R1, MemAct). Out of scope for this project (parametric, tutor-vetoed — see [`scope-and-terminology-decisions.md#2`](../discussion/scope-and-terminology-decisions.md#2-what-reinforcement-learning-means-in-this-projects-title)).
- **Dynamic policy *without* parameter updates** — the policy adapts to context but nothing is trained. **SSGM frames these as closer to what this project proposes** — deterministic / heuristic rules that react to context, no gradient anywhere.

## How memories evolve — techniques SSGM catalogues (added 31/08/2026, Rafael reading)

- **Reflection / self-supervised memory.** The agent critiques its own trajectory and writes the lesson back to memory. SSGM: *"This reflective loop has become a cornerstone of agent improvement (Madaan et al., 2023; Wang et al., 2023)."* This is exactly the Update Engine's ExpeL-style reflection (component C) — SSGM treats it as the well-established default mechanism, not a novelty. *(Madaan et al., 2023 / Wang et al., 2023: cited by SSGM; no arXiv IDs pulled — verify before citing independently.)*
- **RL-driven evolution** — memory operations improved by a reward signal. **Not this project's approach.**
- **Consolidation with forgetting — "forgetting-by-design".** SSGM cites work demonstrating, via the **FiFA benchmark**, that **bounded, budget-aware forgetting policies** (e.g. **Priority Decay**) don't just cut computational cost — they *actively preserve* narrative coherence and privacy *without* sacrificing functionality. *(FiFA / Priority Decay: cited by SSGM; no arXiv ID pulled — verify before citing independently.)* **For this project:** direct support for component E — forgetting as a first-class design goal, not damage control. "Budget-aware" ≈ the volumetria concern the tutor raised on 28/08; "privacy" ties to the LGPD dimension of the still-open `ACL(μ, uid)` gap.
- **Episodic Context Reconstruction — E-mem** (Wang et al., 2026, arXiv:2601.21714 — [`reading-queue.md`](reading-queue.md) #43). Shifts from retrieving pre-stored blocks to the agent *actively reconstructing* context from fragmented traces at read time, for higher fidelity to the original experience. SSGM presents it as the reconstruction-over-retrieval direction. **For this project:** adopt the *argument* (don't destroy context by pre-compressing the trace — supports the 27/08 "trace = full trajectory" decision), not the multi-agent read-time mechanism (cost/latency against the hot path). Fuller fit analysis in the queue entry.

## SSGM's error taxonomy for a memory layer (added 31/08/2026, Rafael reading)

A reusable contribution independent of the framework itself: the failure modes a memory layer can exhibit, in four families.

| Family | Failure modes | Where it bites this project |
|---|---|---|
| **Stability** | semantic drift · procedural drift · goal drift | The Commit Gate (D) exists largely to bound this — versioned, reviewed strategy-layer writes; the "static policy" choice also limits drift by construction. |
| **Validity** | hallucination · temporal obsolescence | NLI contradiction check (D) targets hallucination-into-memory; Weibull decay + hard-delete (E) target temporal obsolescence — the exact gap Mem0 leaves open (forgets only by contradiction, never by age). |
| **Efficiency** | retrieval latency · index bloat | The SAGE-style promotion gate (log→LTM, ~20–30 % promoted) is precisely an index-bloat control; retrieval latency is already a Sub 3.6 metric. This is the tutor's 28/08 volumetria concern, named. |
| **Safety** | memory poisoning · privacy leakage | Memory poisoning ≈ why signal quality is gated (Casper-informed checks in D) and why ADD is system-triggered, not agent-decided; privacy leakage ≈ the LGPD / ACL dimension of the open `ACL(μ, uid)` gap. |

Every one of the four families maps onto a component already in the design — worth carrying into Sub 3.6 (métricas) and the Sub 2.2 architecture doc as an evaluation lens.

### H1 — Governance gates statistically bound drift magnitude

**SSGM's claim (from Theorem 1):** agents equipped with `G_write` (the Write Validation Gate) and `R` (the reconciliation operator) exhibit an **asymptotic upper limit** on drift `δ(M_T, K_true)` over infinite-horizon tasks (e.g. `T > 100` turns); baseline agents without them show **approximately linear** drift accumulation.
**SSGM's evaluation protocol:** a long-horizon benchmark such as **LongMemEval** (Wu et al., 2025), with **LLM-as-a-Judge** and **BERTScore** quantifying the fidelity of the final memory graph against ground-truth text over extended timesteps.

**For this project:** the project's own thesis, restated as a measurable hypothesis. Test = **ablation** — run with the Commit Gate (D) + reconciliation/replay (E) on vs. off, over a long horizon, and check whether the gated version's drift curve flattens while the ablated one grows linear. Substitutions: `K_true` ≈ the manually annotated gold standard (Sub 3.6 Reference Accuracy, still blocked on Sub 1.4 + 1.5); the drift measure ≈ BERTScore / LLM-judge fidelity, or the **Agent Stability Index** (ASI, [`reading-queue.md`](reading-queue.md) #45) as a richer candidate; the long-horizon benchmark ≈ replayed sequences of real annotated cases rather than LongMemEval (per the Sub 3.6 scope decision — a legal-flow gold standard, not a generic benchmark). Already there: the two-layer split, the gate, the replay path. Missing: the drift metric and a horizon long enough for the curves to diverge.

### H2 — Access-scoped retrieval lowers adversarial leakage risk

**SSGM's claim:** enforcing the constrained retrieval rule (Eq. 5 — the `ACL ∧ freshness` filter over Top-K) **dramatically lowers the successful injection rate of cross-tenant adversarial prompts** without degrading the primary task success rate.
**SSGM's evaluation protocol:** simulate **multi-user role-playing scenarios**; deliberately inject adversarial data into **neighbouring graph nodes**; measure the **"Leakage Plateau"** (Liu et al., 2025a).

**For this project:** re-scoped — the write path is system-triggered, not agent/user-decided, so the "cross-tenant adversarial injection" threat is narrower; the live concern is **accidental cross-domain visibility + LGPD** (a cível-domain agent retrieving a trabalhista trace). Test = a **probe set** — authorised vs. unauthorised retrievals against a store with `ACL(μ, uid)` enforced vs. bypassed, measuring unauthorised-retrieval rate *and* confirming task success rate is unchanged. Candidate mechanism under test: **Collaborative Memory** (Rezazadeh et al., [`reading-queue.md`](reading-queue.md) #44) — private/shared tiers + immutable provenance. A Sub 2.5 (security requirements) input and a candidate additional Sub 3.6 metric. Missing: the `ACL(μ, uid)` mechanism itself is still an open gap.

### H3 — the latency vs. coherence trade-off

**SSGM's claim:** putting strict logical-contradiction checks **on the critical path** (Eq. 6) yields a **measurable increase in memory write latency**.
**SSGM's evaluation protocol:** quantify the trade-off — potentially showing that **asynchronous governance** (running `R` during idle periods) achieves high coherence (low `δ`) without hurting immediate conversational fluidity (Zhang et al., 2025).

**For this project:** the formal version of the hot-path / cold-path split the architecture already commits to — the contradiction check (NLI) lives on the **cold path** (Commit Gate, batched), never on `recall_memory` or the episodic ADD, precisely to keep write/read latency flat. H3 says: measure it. Test = report **write/read latency and coherence (`δ`) together, as a trade-off curve**, sweeping governance intensity (contradiction check on the critical path vs. batched; reconciliation cadence `N` small vs. large — the Theorem 1 knob is one point on this curve). Sub 3.6 already names latency as a metric; H3 says pair it with the stability axis rather than reporting them independently. Also gives a name to the tutor's 28/08 scepticism about "elaborate retrieval" for a narrow-scope agent — an implicit H3 argument.

### Net: implementing close to SSGM buys the evaluation almost for free

Because the design already mirrors SSGM (distributed rather than centralised — see the [layer mapping](../discussion/knowledge-as-infra-architecture-hypothesis.md#ssgm-layer-mapping-added-27082026)), each hypothesis comes with a ready ablation: **gate on/off** (H1), **ACL enforced/bypassed** (H2), **check on critical path / batched** (H3). Caveat: these are SSGM's hypotheses about its *centralised* middleware — testing them here also tests whether the *distributed* version preserves the same properties, a finding worth reporting in the M1 deliverable on its own.
